## 0. 一句话结论

**这张表不是「工资应该涨多少」的独立设计，而是「守住房价收入比」的约束解。** 唯一稳定的做法是让薪资曲线与房价曲线**同形**，把 `HOUSE_INDEX(y) / kEra(y)` 锁在一条窄带里。

```js
/* assets/career.js —— CAREER_MULT 新增字段 */
era: {
  /*  knots 与 HOUSE_INDEX 完全对齐（见 §2 为什么必须对齐） */
  table: [
    [1955, 0.35], [1965, 0.46], [1975, 0.66],
    [1985, 1.00], [1990, 1.58], [1995, 1.83], [1997, 1.95], [1999, 1.95],
    [2002, 2.26], [2006, 2.86], [2008, 3.05], [2010, 3.59], [2013, 3.60],
    [2016, 3.65], [2018, 3.94], [2020, 4.43], [2022, 4.93], [2025, 5.31],
    [2028, 5.51], [2035, 5.93], [2045, 6.27], [2065, 6.45]
  ],
  /* 绝对水平归一化：kEra_eff(y) = table(y) / ERA_NORM
     1985=1.00 只是「书写锚点」，真正决定绝对薪资的是 ERA_NORM（见 §3） */
  norm: 5.31            // ← team-lead 裁定（v1.3）：锚在 2025，使 kEra_eff(2025) = 1.00

```

```js

// ... total: base * kEra * kAge * kEdu * kInt * kNet * kLoy
```

## 1. 为什么不能直接用 `FIN_SCALE`

`FIN_SCALE`（data.js:352-355）：
```
[1955, 0.10], [1965, 0.18], [1975, 0.42], [1985, 1.00],
[1995, 1.85], [2005, 2.70], [2015, 3.40], [2025, 4.20], [2060, 5.00]
```

`FIN_SCALE` 是**家庭资产/货币量级**的缩放表，不是工资曲线。把它当工资曲线用有两个硬伤：

1. **`HOUSE_INDEX / FIN_SCALE` 会一路走高**（房价指数跑得比它快得多）→ 晚期房价收入比失控，撞穿 6–15× 买房门。
2. **1955 = 0.10 太低**。0.10 意味着 1955 组的工资只有 1985 的十分之一，前期完全没有可操作的决策空间，直接违反「年代门：1955–1985 组 18 岁家庭净值 −10万~+5万」所隐含的「早期不能穷到无法决策」。

## 2. 设计方法：`kEra(y) = HOUSE_INDEX(y) / R(y)`

定义 **房价收入比指数** `R(y) = HOUSE_INDEX(y) / kEra(y)`。
只要 `R` 的极差 ≤ 1.6，房价收入比就在全年代保持同量级。

**R 的目标形状**（`1985 = 1.00`，缓升到 `2065 = 1.55`）：
- 让晚期买房**略难一点**（真实感：房子越来越贵），但最多只难 55%；
- 1999 与 2025 两段房价回调时，R 回落到 1.00（那两年房子相对便宜）——这也是真实的。

| y | `HOUSE_INDEX` | 目标 `R` | `kEra = HOUSE / R` |
|---|---|---|---|
| 1985 | 1.0 | 1.00 | **1.00** |
| 1990 | 1.9 | 1.20 | **1.58** |
| 1995 | 2.1 | 1.15 | **1.83** |
| 1997 | 2.2 | 1.13 | **1.95** |
| 1999 | 1.95 | 1.00 | **1.95** |
| 2002 | 2.6 | 1.15 | **2.26** |
| 2006 | 3.6 | 1.26 | **2.86** |
| 2008 | 3.9 | 1.28 | **3.05** |
| 2010 | 3.7 | 1.03 | **3.59** |
| 2013 | 3.6 | 1.00 | **3.60** |
| 2016 | 4.3 | 1.18 | **3.65** |
| 2018 | 5.2 | 1.32 | **3.94** |
| 2020 | 6.2 | 1.40 | **4.43** |
| 2022 | 7.4 | 1.50 | **4.93** |
| 2025 | 6.9 | 1.30 | **5.31** |
| 2028 | 7.6 | 1.38 | **5.51** |
| 2035 | 8.6 | 1.45 | **5.93** |
| 2045 | 9.4 | 1.50 | **6.27** |
| 2065 | 10.0 | 1.55 | **6.45** |

### 2.1 ⚠️ 为什么 knots 必须与 `HOUSE_INDEX` 完全对齐

两张表 knot 一致时，任意区间内 `HOUSE` 与 `kEra` **都是 `y` 的线性函数**，因此 `R(y) = 线性/线性` 在区间内**单调**，极值只可能出现在区间端点 = knot 上。

> **这条让 R 的全局极值可被穷举验证**，而不是靠采样碰运气。若 knots 错开，段内会出现 R 的鼓包，极差可能悄悄超标。**请工程侧务必保持 knot 对齐，并在改 `HOUSE_INDEX` 时同步改这张表。**

## 3. `ERA_NORM`：绝对水平归一化（**必读，否则薪资会整体膨胀 6 倍**）

> **`1985 = 1.00` 只是书写锚点，不是绝对水平。**
> `JOBS[].salary` 是按**当下（约 2015–2025）名义水平**写死的（程序员 lv0 = 30,000,000 内部 ≈ 16.7 万 RMB/年；前台/文员 = 16,000,000 ≈ 8.9 万 RMB/年——都是 2020 年代的量级）。
> 如果直接把 `kEra` 乘上去，2025 年的程序员会拿到 `30M × 5.31 = 159M`（≈88 万 RMB），**整体膨胀 5 倍**，全部经济回归门的量级都要重来。

解法：除以一个归一化常数，使**参照年附近 `kEra_eff ≈ 1`**。

```js
kEra_eff(y) = tableAt(CAREER_MULT.era.table, y) / CAREER_MULT.era.norm
```

**`ERA_NORM` 的推演**（关键性质：**极差是尺度不变量**，所以归一化不影响任何绑定约束，只影响绝对水平）。

> ⚠️ **v1.3 修正**：v1.0–v1.2 这里写的是 `房价收入比 = R × NORM`，**漏了一个常数因子**。
> 正确的式子是 `房价收入比 ≈ 1.25 × R × NORM`，其中 `1.25 = (base_house / base_salary) / 属性乘子 = (78M / 48M) / 1.298`。
> 也就是说**绝对比值依赖「哪份工作买哪套房」这个具体配对**，`R × NORM` 只是相对量。下面按修正后的因子重列。

**✅ `ERA_NORM = 5.31`（team-lead 裁定，2026-S1）** —— 锚在 **2025**，即 `kEra_eff(2025) = 1.00`：

| `ERA_NORM` | 房价收入比区间 `≈ 1.25 × R × NORM`（R ∈ [1.00, 1.55]） | 是否符合 6–15× |
|---|---|---|
| 4.43（归一化在 2020） | 5.54× – 8.58× | 🟡 偏低 |
| **5.31（裁定值）** | **6.64× – 10.29×** | ✅ **最贴近 `balance-analysis` 的现实锚点 8–10×** |
| 6.50（v1.2 原值） | 8.13× – 12.59× | 🟢 仍在门内，但偏高 |
| 9.00 | 11.25× – 17.44× | 🔴 冲破 15× 上限 |

**裁定理由（team-lead）**：收支同缩放后「结余/收入比」是 `norm` 不变量，`norm` 的唯一作用是决定 `kEra_eff = 1.0` 落在哪年。**锚在 2025 可让 2025 世代与今天的基线完全一致、可直接比对。**

**验算（`ERA_NORM = 5.31`）**：一本生，`programmer` 入职 lv1（`salary 48,000,000`），25 岁，INT 65 / NET 40 / LOY 30（属性乘子 ≈ 1.298），买 `h_apt_gangbuk`（`base 78,000,000`）：

| 年份 | `kEra_eff` | 年薪 | 房价 | **房价收入比** |
|---|---|---|---|---|
| 1995 | 1.83/5.31 = 0.345 | 21.5M | 78M × 2.1 = 163.8M | **7.61×** ✅ |
| 2015 | 3.63/5.31 = 0.684 | 42.6M | 78M × 4.3 = 335.4M | **7.87×** ✅ |
| 2025 | 5.31/5.31 = **1.000** | 62.3M | 78M × 6.9 = 538.2M | **8.63×** ✅ |
| 2065 | 6.45/5.31 = 1.215 | 75.7M | 78M × 10.0 = 780M | **10.31×** ✅ |

**全年代落在 7.6× – 10.3×，稳稳在 6–15× 内，且随年代缓慢上升（真实感），正中现实锚点 8–10×。**

同时校验「普通打工人年薪 800万–2000万 内部」的参照：`clerk` lv0（`16,000,000`）× `kEra_eff(2025) 1.000` × 属性乘子 ≈ 1.2 → **≈ 1,920 万**，**刚好压在 2000 万上限内** ✅（余量 4%）。

> ⚠️ **这条余量只有 4%，比 norm = 6.50 时紧**（那时 1,570 万，余量 21%）。**回归时若 `clerk` P90 触顶，优先调 `SCORE_K.max`（教育与职业 Spec），不要调 `norm`** —— `norm` 一动，房价收入比与 2025 锚点同时失效。

### 3.4 ⚠️ `livingCost()` 必须同步乘 `kEra_eff`（**v1.1 新增，engineering-lead 实测触发**）

> **这是 C-2 的一条硬连带，不是可选项。谁先落谁先炸。**

**实测事实**（`engine.js:1423-1431`）：`livingCost()` **完全不随年代缩放**——它只用 `JOBS[].cost`（默认 12,000,000）+ 固定加项（`gangnam_owner` +1500万 / `married` +1200万 / 每孩 +600万 / 离异抚养费 +300万）。而 `familyIncome()`（:389）**是**按 `FIN_SCALE` 缩放的。

于是有三条互不相干的曲线：`FIN_SCALE`（家庭收入）、`kEra`（个人年薪，**本表新增**）、固定值（生活支出）。只加 `kEra` 会让「收入 / 支出」这个比值整体 ×`kEra`：

| 年份 | `kEra_eff` | 程序员 lv1 年薪 | 有家庭的年支出 | 年结余 |
|---|---|---|---|---|
| 1985 | 0.154 | 9.6M | 30M | **−20.4M** ❌ |
| 2002 | 0.348 | 21.7M | 30M | **−8.3M** ❌ |
| 2015 | 0.559 | 34.8M | 30M | +4.8M |
| 2025 | 0.817 | 50.9M | 30M | +20.9M |

→ engineering-lead 实测「1980–2002 出身玩家约 45% 年度结余为负」，**与我的推演一致**。

#### 3.4.1 结论：**C-2 与「`livingCost` 不缩放」不可兼得**

- C-2 要求 `kEra(2025)/kEra(1985) ≥ 3.5` → 早期收入 ≤ 2025 的 **28.6%**；
- 支出固定 30M → 早期收入必须 ≥ 30M 才不亏；
- 而 2025 年程序员年薪若 ≥ 30M/0.286 = 105M，则 `clerk` lv0 会到 ~35M，**冲破「普通打工人年薪 800万–2000万内部」参照上限 75%**。

**两条不能同时成立。** 唯一一致的解法是**让支出与收入同缩放**：

```js
// engine.js:1430 —— livingCost 返回前
return cost * kEraEff(state);   // kEraEff(y) = tableAt(CAREER_MULT.era.table, fmtYear(state)) / CAREER_MULT.era.norm
```

**这样做之后**：`年结余 = kEra_eff × (收入 − 支出)` —— **「收入/支出」比值回到与今天完全一致**，`norm` 只影响「结余 / 房价」这一个比值（而这正是 §3 的 **5.31** 所标定的）。**C-1~C-4 全部不受影响**（极差与比值都是尺度不变量）。

#### 3.4.2 一个反直觉但重要的点：本表与 `FIN_SCALE` 形状几乎相同

把本表的**原始值**（未除 `norm`）与 `FIN_SCALE` 对齐看：

| 年份 | `FIN_SCALE` | 本表原始值 | 比值 |
|---|---|---|---|
| 1985 | 1.00 | 1.00 | 1.000 |
| 1995 | 1.85 | 1.83 | 1.011 |
| 2005 | 2.70 | ≈2.71 | 0.997 |
| 2015 | 3.40 | 3.63 | 0.937 |
| 2025 | 4.20 | 5.31 | **0.791** |
| 2060 | 5.00 | ≈6.33 | 0.790 |

→ **本表 = `FIN_SCALE` 的形状 + 一段更陡的晚期（2025 后多涨 21%）**。那段陡峭正是为了守 `HOUSE_INDEX/kEra ≤ 1.6`。
→ 也因此：**个人收支用 `kEra`、家庭收支用 `FIN_SCALE`，两者在 1985–2015 段几乎重合（误差 ≤6%）**，不会造成「家庭很有钱但个人很穷」的观感分裂。2025 后差 21%，属可接受。

#### 3.4.3 我不推荐的替代方案

| 方案 | 做法 | 为什么不推荐 |
|---|---|---|
| 抬高 `norm` 让早期不亏 | `norm ≈ 2.3` → `kEra_eff(2025) = 2.31` | 2025 年 clerk 到 45M，**冲破年薪参照 2.25 倍**；且房价收入比掉到 2.3×，买房门彻底失效 |
| 支出用更缓的曲线 `kEra^0.7` | 早期支出相对更高 | 有年代感（早期更苦），但**早期结余仍可能为负**，需完整回归才能定，风险高 |
| 放弃 `kEra`，只调 `HOUSE_INDEX` | 把房价曲线压平 | 直接违反 C-3 的设立目的（晚期房价收入比失控）；且要重推买房门与 `RATE_TABLE` |

**推荐：支出与收入同用 `kEra_eff`（最简、零回归风险、比值全部守恒）。**

### 3.5 三件套：4b-2 / 4b-3 的裁定与判据（**v1.2，回应 engineering-lead `era-lifecycle-verify`**）

> 结论：**4b-2 认（但定性要改）；4b-3 认（但必须先扫描）；A-07 的判据必须从「静态快照」改成「轨迹」。**

#### 3.5.1 ⚠️ 关键纠正：39.2 年这个数有两个方法学问题，不能直接当判据

1. **它按「全款」算，而游戏不是全款。**
   `buyProp(state, kind, refId, downRatio, qty)`（market.js:403）→ `const loan = total - down;`（:418）。
   UI 提供 **首付 30% / 50% / 全款**（ui.js:1739-1741），**默认实用路径是 30%**。
   → 1955 静态值按比例应为 `39.2 × 0.3 ≈ **11.8 年**`，不是 39.2。
2. **它按「静态费率」算，而玩家工资随年代上涨。**
   39.2 = `房价 /（1955 年的年结余）`，即假设玩家一辈子拿 1955 的工资。**而 1955 世代的工资在一生中涨 6.5×** —— 这正是本表存在的唯一理由。

**修正后的判据（EW-8）：轨迹测试，不是快照测试。**
> 模型：22 岁工作，**每年结余 = `kEra_eff(y) × (名义收入 − 名义支出)`**，逐年累积；购房条件 = **累积结余 ≥ 30% × `base × HOUSE_INDEX(y)`**（`h_apt_gangbuk`，base 78M），且 `y ≥ HOUSES[].minYear`。
> 输出：**首次购房年龄**，按出生年 1955 / 1975 / 1985 / 2005 四组。

**我的手算预期**（`B` = 名义年结余 ≈ 37M，`programmer` lv1 口径）：

| 世代 | 首次可买年 | 需首付 | 累积曲线 | **首次购房年龄** |
|---|---|---|---|---|
| 1955 | 1985（`minYear` 下限） | 23.4M | 1977–1985 已累 ≈43M | **30**（1985 市场一开门就买） |
| 1985 | 2007 | 87.7M | 16.8M/年 → 5.2 年 | **27** |
| 2005 | 2027 | 172M | 31M/年 → 5.6 年 | **28** |

→ **预期极差 ≤ 3 岁。若实测落在 27–32 岁且极差 ≤ 5 岁，本表判定通过。**
→ 1955 组略晚（30 岁）**不是 `kEra` 造成的**，是 `minYear = 1985` 的市场未开放等待，叙事上正确（「那会儿还没商品房」）。

#### 3.5.2 4b-2（`HOUSE_INDEX` 补 1955–1985 下降段）：**v1.3 撤回 —— 确认为 no-op，不改**

**team-lead 的质疑成立，我撤回 v1.2 的采纳。** 他的原则是对的：

> 「改一个行为影响为零的东西来让指标通过，是买指标不是修游戏。」

**我把 `HOUSE_INDEX` 的全部调用点扫完了，确认它是彻底的 no-op：**

| 位置 | 用途 | 1955–1985 是否可达 |
|---|---|---|
| `market.js:412` | `buyProp` 计算成交价 | ❌ 被 `market.js:410` `if (y < (ref.minYear \|\| 1985)) return { ok:false }` 硬拦 |
| `market.js:348` | **已持有**房产的估值 | ❌ 1985 年前不可能持有 |
| `ui.js:1728` | 房价展示 | ❌ 无房可列（`minYear` 过滤） |

**`HOUSE_INDEX` 在 `assets/` 里只有这一个函数（market.js:237 `housePrice`）在用，全表仅此 3 个调用点。**

**并且，team-lead 问的那个关键点我查了：出身资产 / 遗产不走 `HOUSE_INDEX`。**
- 出身家庭资产 = `initFamilyFin()`（engine.js:365），取 `tableAt(FIN_SCALE, startYear)` —— **是 `FIN_SCALE` 域**；
- 遗产 `inherit_at_*`（engine.js:1664/1668）的金额来自 `fin.assets`，同样是 **`FIN_SCALE` 域**。

→ **两条域完全不交叉。** 所以「1955 世代有房家庭的资产是否该按 `HOUSE_INDEX(1955)` 折算」这个问题**不成立**：出身资产从来就不是按房价指数算的。

**最终处置（采纳 team-lead 的方案）**：
- **不改 `HOUSE_INDEX`。** 改一个永不被读取的数据点来让指标变绿，还会留一个陷阱（将来谁调 `minYear` 或加早期房产，它会静默变成活数据）。
- **C-3 的豁免从「R 极差」扩大为「房价 / 储蓄比极差」，即由 EW-8（轨迹验收）承担**，豁免理由在文档写明：**1985 年前购房物理不可达（`market.js:410`）**。
- §4.1 保留为「物理不可达」的正式豁免条款，不再需要 team-lead 二选一。

但**「家庭侧」的金额在调用 `applyEffects` 之前就已经手动乘过 `FIN_SCALE` 了**。全部 6 个调用点：

#### 3.5.6 `FIN_SCALE` 与本表在 1955 段差 250% —— **见 §3.6，已单独立项 4b-4**

engineering-lead 指出这条观感分裂风险。**我的判断：接受，不改。**
- 两者管的是**不同主体**：`FIN_SCALE` 管**家庭的钱**（父母资产/收入/医疗/彩票），`kEra` 管**玩家自己的年薪**。玩家 18 岁前没有个人年薪，两条曲线在玩家有收入之前**不交汇**。

## 3.6 4b-4 · `FIN_SCALE` 是第四条曲线（**team-lead 单独立项，本节给方向与影响面评估**）

### 3.6.1 我的裁定：**原则同意统一，但方向不是「把 `FIN_SCALE` 抬到 `kEra」；本批不动，排到 v6.0 数值重铸**

**先把「名义标度」这件事说清楚。** 一个世界里只能有一个名义价格水平。现在有两条，是**历史欠账**（`FIN_SCALE` 先有，`kEra` 是 A-07 新加），不是设计意图。所以**原则上必须统一** —— 这点我同意 team-lead。

**但三个方向我逐个否掉两个：**

| 方向 | 判定 | 理由 |
|---|---|---|
| **抬 `FIN_SCALE` 到 `kEra` 形状**（早期 0.10 → 0.35） | ❌ | `FIN_SCALE` 管的是**已验收的出身/家庭系统**。早期家庭资产 ×3.5 → **出身优势在早期被放大 3.5×**，直接冲击**年代门（1955–1985 组 18 岁家庭净值 −10万~+5万）**与出身分布。这等于把 A-07 的范围扩到「整个出身系统」 |
| **压 `kEra` 到 `FIN_SCALE` 形状**（1955 → 0.10） | ❌ | `kEra_eff(1955) = 0.10/5.31 = 0.019`（名义薪资的 1.9%），**早期彻底无法决策**，直接违反 C-4 的设立意图 |
| **都不动，留到 v6.0 统一** | ✅ | 见下 |

### 3.6.2 为什么「本批不动」是安全的：**两条曲线的读取窗口几乎不重叠**

| | 最早被读取的年份 | 说明 |
|---|---|---|
| `FIN_SCALE` | **1955**（出生年，`initFamilyFin` 取 `startYear`） | 玩家一出生就在读 |
| `kEra` | **约 1973**（最早出生 1955 + 18 岁） | 只在有工作/有收入时读 |

→ **1955–1972 这段 `kEra` 根本不会被读取**（那段时间没有任何玩家在工作）。
→ 真正的分歧区只有 **1973–1985 这 12 年**，且只有 **1955–1967 出生**的玩家会在那期间同时看到两条曲线 —— 那时他们刚入职、收入低、家里也穷。**暴露面很窄。**

**并且晚期两条曲线并不离谱**：1995 差 1%、2015 差 7%、2025 差 26%、2060 差 29%。真正的问题只在 1955–1975。

### 3.6.3 影响面评估（回答 team-lead 的两个担心）

**担心 A：不统一 → 1955 世代的家庭资助相对个人经济只有 1/3.5。**
→ 实际影响：家庭资助走 `FIN_SCALE`（低），个人薪资走 `kEra`（相对高）。结果是**早期世代「靠自己」比「靠家里」更划算**。
→ **这在设计上不是缺陷，反而是一条可辩护的年代叙事**：1955–1975 世代家里本来就没钱（`FIN_SCALE` 0.10–0.42 是对的），而个人工资被 C-4 地板托住了。**「穷家庭里的孩子反而更能靠工资翻身」是一个正向的、符合直觉的早期体验。**
→ 反过来说，若统一（抬 `FIN_SCALE`），早期会变成「家里有钱的更有钱」，**出身决定论被放大** —— 这是我不想要的。

**担心 B：统一 → 出身优势在早期被放大 3.5×。**
→ 同 A。这正是我否掉「抬 `FIN_SCALE`」的核心理由。

### 3.6.4 本批的最小动作（零风险，建议顺手做）

1. 在 `career.js` 的 `CAREER_MULT` 与 `engine.js` 的 `FIN_SCALE` 上方各加一行注释，写明：**「`kEra` 与 `FIN_SCALE` 是两个不同的名义标度，v6.0 数值重铸时统一为一条」**，防止后人误以为同源而混用。
2. 回归时看一眼：1955–1975 世代**工作后**是否出现「父母给的钱比自己年薪高一个数量级」的割裂感。若出现，兜底是**把家庭转账类事件纳入 4b-3 的 `kEra` 缩放**（那时它们就落在同一条曲线上了）。

**结论：4b-4 不阻塞本批（与 team-lead 判断一致）；优先级排在「出身分布重审」之后，作为 v6.0 数值重铸的一部分统一处理，不单独立项。**

## 5. 这张表的代价（诚实记录）

为了守住房价收入比，薪资曲线被迫与房价曲线**高度同形**。表现为两处「走平」：

| 区间 | `kEra` | 年化 | 叙事解释 |
|---|---|---|---|
| 1997 → 1999 | 1.95 → 1.95 | 0% | 亚洲金融风暴后，薪资停滞 ✅ 真实 |
| 2022 → 2025 | 4.93 → 5.31 | 2.5%/年（前段 4.6%） | 楼市下行期，涨薪放缓 ✅ 真实 |

**这是有意取舍：宁可让薪资曲线不光滑，也不能让晚期买房变成不可能。** 而且两段走平恰好落在两个真实的「薪资增速放缓」年份，叙事上站得住。

> 若回归后觉得 2008→2013（3.05 → 3.60，年化 3.4%）那段太平，可以把 `R(2010)` 从 1.03 压到 1.00、`R(2013)` 保持 1.00，换取约 +3% 的薪资增速——但会吃掉 C-3 的余量，**不建议**。
