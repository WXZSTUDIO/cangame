> 适用前提：零构建纯静态（8 个 `<script>` 顺序加载）、GitHub Pages 托管、小程序已冻结。

## 0. 结论先行

| | |
|---|---|
| **推荐方案** | **P2 · `defer` + 事件按人生阶段拆 4 个文件** |
| **交付节奏** | **两段式**：先只做 P1（8 个 `defer` 关键字，本批就能落地，零风险），S2 事件扩容前再做 P2 的分段改造 |
| **为什么是 P2 而不是 P3（JSON + fetch）** | P3 会让「生产加载路径」和「31 个测试脚本的 vm 加载路径」**分叉**——这个项目全部安全网都建立在 vm 同步加载上，分叉意味着最容易出事的时序代码恰好没测试覆盖；而且 P3 会让 `file://` 双击打开直接失效 |
| **为什么"加内容不加首屏时间"成立** | P2 下首屏下载的事件量只跟**当前所处人生阶段**有关，跟事件库总量**无关**。3G 弱网可玩时间 857 ms，241 条是它，500 条还是它 |

**一句话**：FCP 的瓶颈从来不是 CPU，而是「8 个脚本同步阻塞渲染」。这一层只需 8 个 `defer` 就解决，拿到 **−80% FCP**。事件分段解决的是**第二阶段**的问题——让 S2 把事件从 241 加到 500+ 时，首屏时间**不动**。

### 1.2 `EVENTS` 是怎么组装的（**更正主理人的记忆**）

主理人原话：「engine.js 里多处直接引用，data.js 加载末尾会把子数组 push 合并进 EVENTS」。实测更正两点：

1. **合并点有 4 处，但不在文件末尾**，而是「每个池声明完之后立刻合并」：
   - `data.js:1335` `EVENTS.push.apply(EVENTS, EVENTS_EXTRA);`
   - `data.js:1584` `EVENTS.push.apply(EVENTS, EVENTS_FAMILY);`
   - `data.js:1780` `EVENTS.push.apply(EVENTS, EVENTS_FAMILY2);`
   - `data.js:1819` `EVENTS.push.apply(EVENTS, EVENTS_ERA);`

   → 这意味着**今天 `EVENTS` 在 `data.js` 执行完的那一刻就已经是完整的 241 条**，不是一个「加载期逐步填充」的数组。任何懒加载方案都必须处理这个合并时机。

2. **`assets/` 内 `EVENTS` 的引用点只有 1 处**，不是多处：

   | 文件 | 行 | 代码 |
   |---|---:|---|
   | engine.js | 1049 | `const pool = EVENTS.filter(ev => matchEvent(state, ev));` |

   **这是一个非常好的消息**：整个产品代码对事件池的依赖收敛到一个 `filter` 调用。只要「需要时 `EVENTS` 里有货」，这一行**一个字都不用改**。

### 1.3 真正的改造成本大头：`tools/` 与发布白名单

产品代码干净，但**工程侧**不干净：

| 位置 | 数量 | 说明 |
|---|---:|---|
| `tools/*.js` 里写死 `['assets/data.js', ...]` 加载清单 | **29 个文件** | count / era-test / family-test / life-test / sim-test / v5-test / _verify-v5x / _dom-v5x / dom-test / browser-parity-test / _choice-preview / _layers-debug / _portrait-qa / _tune-exam … |
| `production/phase6-polish/perf/scripts/*.js` | **2 个文件** | `harness.js`（核心）、`imp-verify.js` |
| `tools/deploy.py` 的 `PUBLISH` 白名单 | 12 个文件 | **新增文件不加进这个列表，就永远发布不到 GitHub Pages** |

> **这条是整个方案里最容易被忽略、但一定会踩的坑**：`deploy.py` 是白名单发布，不是 `git add -A assets/`。新增 `assets/events-*.js` 之后必须同步改 `PUBLISH`，否则线上 Pages 会 404，而本地与源码仓库一切正常。

### 1.4 事件「时间窗」分布（懒加载的天花板）

`matchEvent()` 用 `ev.age || [0,200]` 做年龄窗过滤（`engine.js:939`）。窗口没开的事件，理论上一辈子都不会被抽到——这就是可推迟空间。

| 年龄 | 窗口已开启条数 | 占比 |
|---:|---:|---:|
| **0 岁（首屏）** | **3** | **1.2%** |
| 6 岁 | 17 | 7.1% |
| 18 岁 | 76 | 31.5% |
| 30 岁 | 182 | 75.5% |
| 60 岁 | 236 | 97.9% |
| 70 岁 | 241 | 100.0% |

**可推迟空间：首屏之后仍有 238 条（98.8%）事件窗口未开启。**

按「首次开启年龄」切四段（四段之和 = 241，无遗漏无重叠）：

| 阶段 | 判定规则 | 条数 | 占比 | 事件 gzip (KB) |
|---|---|---:|---:|---:|
| 童年 | `age[0] ≤ 6` | 17 | 7.1% | 2.2 |
| 学生 | `7 ≤ age[0] ≤ 18` | 59 | 24.5% | 7.6 |
| 成年 | `19 ≤ age[0] ≤ 60` | **160** | **66.4%** | **20.6** |
| 晚年 | `age[0] ≥ 61` | 5 | 2.1% | 0.7 |

> 有 30 条事件的窗口**横跨多个阶段**（如 `[10, 40]`）。按「首次开启年龄」归入学生段即可——它们在首开之后一直可用，而学生段一旦加载就不会卸载，正确性不受影响。

### 1.5 关键判断：**不能按现有池切，必须按年龄重组**

| 池 | 童年 | 学生 | 成年 | 晚年 | 合计 |
|---|---:|---:|---:|---:|---:|
| `EVENTS(本体)` | 10 | 41 | 52 | 3 | 106 |
| `EVENTS_EXTRA` | 0 | 5 | 59 | 2 | 66 |
| `EVENTS_FAMILY` | 4 | 3 | 24 | 0 | 31 |
| `EVENTS_FAMILY2` | 0 | 3 | 25 | 0 | 28 |
| `EVENTS_ERA` | 3 | 7 | 0 | 0 | 10 |

除 `EVENTS_ERA` 外，每个池都**横跨三到四段**。所以「把 `EVENTS_FAMILY2` 单独成一个文件」是无效动作——它在成年段有 25 条、学生段有 3 条，切成文件后首屏还是要下它。**必须按年龄重新分组，把现有 5 个池打散。**

这是 P2 改动量的主要来源，也是它的主要风险来源。

### 1.6 现状加载方式

```html
<!-- index.html:226-233 —— 8 个同步脚本，一个 defer 都没有 -->
<script src="assets/data.js?v=5.5.0"></script>
<script src="assets/market.js?v=5.5.0"></script>
...
<script src="assets/ui.js?v=5.5.0"></script>
```

- `<link rel="stylesheet" href="assets/style.css?v=5.5.0">` 在 `<head>`（第 8 行）
- 无内联 `<script>`
- `ui.js:1989` `document.addEventListener('DOMContentLoaded', init);` —— **启动挂在 DOMContentLoaded 上**
- 静态 body 有 199 行外壳标记（含 topbar「人生模拟 · 中国 1955–2005」）

> **最后一条很重要**：因为有静态外壳，`defer` 之后浏览器能先把外壳画出来（"人生模拟"标题可见），而不是白屏。同时 `defer` 脚本在 DOMContentLoaded **之前**执行完毕，所以 `init` 的时序完全不受影响——**P1 是纯粹的加法，零时序风险**。

## 2. 方案 1：按人生阶段拆成多个文件 + 按需注入（P2）

### 2.1 做法

```
assets/
  data.js              常量表 + 空 EVENTS + 阶段加载器（约 40 行）
  events-child.js      童年段 17 条   (2.2 KB gzip)
  events-student.js    学生段 59 条   (7.6 KB gzip)
  events-adult.js      成年段 160 条  (20.6 KB gzip)
  events-elder.js      晚年段 5 条    (0.7 KB gzip)
```

- `index.html` 首屏只放：`data.js` + `events-child.js`（+ 其余 6 个逻辑层文件），全部加 `defer`
- 每个阶段文件沿用现有模式，各自执行 `EVENTS.push.apply(EVENTS, EVENTS_CHILD)` —— **现有 4 条 `push.apply` 的写法原样搬过去，只是按年龄重新分组**
- 新增 `loadEventStage(band)`：动态创建 `<script>`、`s.async = false`（保持插入顺序）、onload 后把 band 标记为已加载

### 2.2 可行性（逐条对照主理人的问题）

| 问题 | 结论 |
|---|---|
| 多 `<script>` + `defer` 可行性 | ✅ **可行。** `defer` 保序、在 DOM 解析完成后按插入顺序执行、早于 DOMContentLoaded。本项目无内联脚本、无顶层 `const` 跨文件依赖（函数声明会提升），`defer` 完全兼容 |
| **`async` 能用吗** | ❌ **不能用。** `async` 脚本执行顺序不确定，而本项目 `data.js → engine.js → …` 是硬顺序依赖（顶层 `const` 存在 TDZ）。**所有脚本只能 `defer`，不能 `async`** |
| 动态注入的阶段文件顺序 | 用 `s.async = false` 可强制按插入顺序执行（各浏览器稳定支持）。实际上阶段文件之间无相互依赖，顺序并不关键，加上只是保险 |
| 纯静态托管兼容性 | ✅ 完美。新增的只是普通 `.js` 文件，GitHub Pages 默认 `application/javascript`，无 MIME 问题 |
| **`file://` 双击打开** | ✅ **继续可用。** classic `<script>` 在 `file://` 下正常工作（ES Module 才会被 CORS 拦） |
| 与零构建约束冲突吗 | ❌ 不冲突。没有打包器、没有编译步骤，只是手动分组 |

### 2.3 首屏收益

见 §5 对照表。要点：**FCP 收益全部来自 `defer`，不是来自拆分**。拆分带来的是「可开始游戏」再提前 107 ms（3G），以及 §6 的结构性收益。

### 2.4 改动量

| 项 | 量 | 说明 |
|---|---:|---|
| `data.js` | 大 | 5 个池按 `age[0]` 重新分组搬进 4 个新文件；保留常量表与空 `EVENTS`；新增阶段加载器 ~40 行 |
| 新增文件 | 4 个 | `events-{child,student,adult,elder}.js` |
| `engine.js` | **0** | `EVENTS.filter` 一行不改（数组照常增长）✅ |
| `index.html` | +1 行 | 首屏只挂童年段 |
| `tools/` 加载清单 | **29 个文件各 1 行** | 在 `'assets/data.js'` 后插入 4 个阶段文件路径 |
| `perf/scripts/` | 2 个文件各 1 行 | `harness.js` 的 `MODULES`、`imp-verify.js` |
| `tools/deploy.py` | +4 行 | `PUBLISH` 白名单 |
| **估算总改动** | **约 750 行新增/搬迁 + 36 处 1 行改动** | 事件搬家是主体，且**必须脚本化搬运 + 自动校验**，不能手抄 |

### 2.5 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| **事件搬家出错**（漏条、错分、字段损坏） | 高 | 必做回归断言：拆分后 4 段按序拼接 **深等于** 拆分前 `EVENTS`（241 条逐字段比对）。这是可自动化的，也是本方案最强的回归证据 |
| **阶段文件还没加载完就跨段** | 中 | ① 加载策略：**当前段加载完立刻预取下一段**，可获得近乎无限的时间余量；② 兜底：`drawEvent()` 在目标段未就绪时，从**已加载段**里抽（池子小一点，但绝不崩、绝不空） |
| **读档落到高年龄段** | 中 | 存档恢复前，按 `state.age` 同步加载所有已开启段再 `renderGame()`。这会让启动流程变成异步——是 P2 最实质的一处代码改动 |
| 事件 id 全库唯一性校验（sim-test 会查重） | 低 | 测试侧会加载全部 4 段，查照跑 |
| 30 条跨段事件归段争议 | 低 | 规则明确（`age[0]`），可脚本判定 |
| 阶段划分不合理（成年段 66%，一个人扛 20.6 KB） | 中 | 见 §7：成年段可再按 19–30 / 31–45 / 46–60 三刀细分 |

### 2.6 对 `EVENTS` 全局引用的改造成本

| 位置 | 成本 |
|---|---|
| `assets/engine.js:1049` | **0**（一行不改） |
| `assets/` 其他 | **0**（没有其他引用点） |
| `tools/` 29 个脚本 | **各加 1 行**（把 4 个阶段文件加进加载清单）。机械改动，可脚本化批量执行，跑全量回归即可验证 |
| `perf/scripts/harness.js` | **1 行** |
| `deploy.py` | **4 行**（白名单） |

> **关键洞察**：P2 之所以改造成本低，是因为它**保持"同步执行 push 进全局数组"这个模型不变**。生产环境和 31 个测试脚本走的是**同一条加载路径**——测试脚本只要把文件加进清单，vm 里同步执行完毕后 `EVENTS` 就是完整的 241 条，跟今天一模一样。**生产路径与测试路径同构**，这是 P2 相对 P3 的决定性优势。

## 3. 方案 2：事件抽成 JSON + fetch 懒加载（P3）

### 3.1 先纠正我自己一个先验假设（实测推翻）

我原本假设「事件对象里带 `cond` / `effects` 函数，JSON 化不可能」。**实测证明这个假设是错的**：

```
# data-json-feasibility.out.txt
事件总数：241
含函数的事件条数：0 / 241（0.0%）
含其他不可序列化值的事件条数：0 / 241
JSON 往返实测：通过
```

事件的 `cond` 是**声明式对象**（`{need:[flags], ban:[flags], min:{stat}, max:{stat}, job:[...]}`），由 `engine.js:918` 附近解释执行，**不是函数**。（带函数语义的 `a.cond(state)` 在 `engine.js:823`，那是成就系统，不是事件。）

**所以 P3 在技术上完全可行**，事件池是 100% 纯数据，可无损转 JSON。

### 3.2 但 P3 仍然不推荐，原因有四条

**① 它会让 `file://` 双击打开彻底失效。**
`fetch('./events-child.json')` 在 `file://` 协议下被 CORS 直接拒绝（origin 是 `null`）。这个项目是零构建纯静态，双击 `index.html` 就能玩是一条隐含的用户可达路径，也是我们在本地快速验证的常用方式。P3 会把这条路永久关掉。P2 用 `<script>` 就没有这个问题。

**② 测试路径与生产路径分叉——这是最要命的一条。**
现在 29 个 `tools/` 脚本 + `harness.js` 用 `vm.runInContext` **同步**加载 `assets/*.js`。P3 之后：
- 生产：异步 `fetch` → `JSON.parse` → push
- 测试：vm 里没有 `fetch`，只能同步 `fs.readFileSync` + `JSON.parse` → push

**生产路径（异步、有失败、有时序）恰好是测试覆盖不到的那段。** 加载失败兜底、跨段时序、慢网下的空池——这些最容易出 bug 的地方，全部落在测试的盲区里。对一个「安全网 = 31 个 vm 脚本」的项目来说，这是不可接受的结构性风险。

**③ 首屏「可开始游戏」反而更慢。**
P3 的童年段是 fetch 来的，多一个串行 RTT。3G 下 P2 = 857 ms，P3 = **1019 ms**（+19%）。P3 靠「首屏事件量 = 0」省下的 2.2 KB，抵不过多出来的一次往返。

**④ 它要求事件池能容忍"暂时为空"。**
首屏那一瞬间 `EVENTS.length === 0`。今天没有代码在启动期扫描 `EVENTS`（好消息），但这是一颗**未来必然踩响的雷**——任何人加一行「启动时统计事件数」就会在 P3 下拿到 0。P2 的事件在首屏就是同步就绪的，没有这个坑。

### 3.3 GitHub Pages 兼容性（针对主理人点名的问题）

| 项 | 结论 |
|---|---|
| **MIME** | ✅ GitHub Pages 对 `.json` 返回 `Content-Type: application/json`，`fetch` + `response.json()` 正常 |
| **CORS** | ✅ 同源（`/cangame/events-*.json` 与页面同源），无跨域问题。**但 `file://` 场景下 origin 为 `null`，必死** |
| **缓存** | ✅ Pages 对静态资源有 `Cache-Control`（约 10 分钟），现有 `?v=5.5.0` 版本号机制对 JSON 一样有效 |
| **gzip** | ✅ Pages 自动对 `application/json` 做压缩，与 `.js` 无差异 |

→ **GitHub Pages 侧没有任何障碍。P3 的问题不在托管，在架构。**

### 3.4 改动量与风险

| 项 | 量 |
|---|---|
| 事件数据转 JSON | 241 条，需脚本化转换（可行，往返已验证） |
| 新增 JSON 文件 | 4 个 |
| `data.js` | 删 5 个池，加异步加载器（含失败重试、降级）~80 行 |
| `index.html` | 改 1 行 |
| `tools/` 29 个脚本 | **各 1 行 + 需要额外注入 fetch 垫片或改读文件**（比 P2 复杂：vm 里没有 fetch，得改造加载器本身，不是简单加路径） |
| `deploy.py` | +4 行 |
| **风险** | 加载失败降级路径、首屏空池时序坑、测试/生产路径分叉、`file://` 失效、**未来维护者踩空池雷** |

## 4. 方案 3：保持单文件 + 推迟非首屏数据解析（P4）

### 4.1 结论：**这一条对首屏无效，是个伪方案**

理由：对 `<script>` 而言，**解析就是执行**。一个顶层数组字面量：

```js
const EVENTS_EXTRA = [ {...}, {...}, ... ];  // 66 条
```

浏览器下载完这一块字节，解析它的同时就执行了它——没有"先跳过、回头再解析"的机制。要让"延迟解析"生效，前提是**这段数据在另一个文件里**，而那已经是 P2 了。

P4 唯一能推迟的是**派生物**（比如预先建好的索引、预先算好的分组）。但实测：`assets/` 里对 `EVENTS` 只有 1 处 `EVENTS.filter(...)`，**没有任何预建索引**。所以 P4 无事可做。

### 4.2 补充：CPU 本来就不是瓶颈

我之前测过：冷启动逻辑层「编译 + 执行」**只有 8 ms**。就算把事件解析的耗时砍到 0，也只省下个位数毫秒——相对 3G 下 2596 ms 的网络耗时，是噪声。

> **P4 在本次讨论中应予排除。** 它的价值在于纠正常见误解：「优化首屏」在这个项目里 = 优化**网络与阻塞**，不是优化解析。

### 5.1 关键路径耗时（模型：`data-load-model.js`，参数全部实测）

**3G 弱网（1.5 Mbps / RTT 150 ms）**

| 方案 | 首屏 FCP | 可开始游戏 | FCP 收益 |

## 6. 推荐：P2（分两段交付）

### 6.1 为什么是 P2

1. **它扛得住 S2 的真正需求。** S2 要把事件从 241 加到 500+、新增 15 条职业线。P2 是唯一能给出「首屏时间与事件总量解耦」这一**结构性保证**的方案（P1 做不到，P3 做得到但代价更高且更慢）。
2. **生产与测试路径同构。** 31 个测试脚本照常 `vm` 同步加载，只是清单多 4 行。P3 会把最容易出事的异步路径扔进测试盲区。
3. **`engine.js` 零改动。** 整个产品代码对事件池的依赖就是一个 `filter`。
4. **不损失 `file://` 可达性**，不引入 fetch 的失败路径，不引入 CSP 顾虑。
5. **改造是机械化的、可校验的。** 事件搬家可以脚本化，正确性用「拼接后深等于拆分前」一条断言锁死。

### 6.2 但必须分两段交付，不能一次上

**阶段 A（本批或下一批，今天就该做）：只做 P1。**

- 改动：`index.html:226-233` 加 8 个 `defer`。**就这么多。**
- 收益：**−80% FCP**（3G 2596 → 522 ms）
- 风险：**零**。`defer` 脚本早于 DOMContentLoaded 执行，`ui.js:1989` 的 `init` 时序不变；无内联脚本；无顶层 `const` 跨文件依赖问题（函数声明会提升）
- 验证：全量 `tools/` 回归 + `browser-parity-test` + 人工开一次弱网节流

> **P1 一个人就吃掉了全部 FCP 收益的 100%。** 它和 P2 的分段改造完全解耦，先落地、先受益、零风险。

**阶段 B（S2 事件扩容开工前）：做 P2 的分段改造。**

前置条件：事件库基本定型（否则搬一次家再改一次，白干）。

### 6.3 P2 落地设计（阶段 B 的详细设计）

**① 文件与分组规则**

```
assets/events-child.js    age[0] ≤ 6          17 条   2.2 KB gzip
assets/events-student.js  7 ≤ age[0] ≤ 18     59 条   7.6 KB gzip
assets/events-adult.js    19 ≤ age[0] ≤ 60   160 条  20.6 KB gzip
assets/events-elder.js    age[0] ≥ 61          5 条   0.7 KB gzip
```

每个文件顶层：`const EVENTS_CHILD = [ ... ]; EVENTS.push.apply(EVENTS, EVENTS_CHILD);`
—— **沿用现有写法，只是按 `age[0]` 重新分组**（不能用现有池，见 §1.5）。

**② 成年段建议再细分**

成年段 160 条 / 20.6 KB，一个人扛全部事件 gzip 的 66%。建议在 P2 里直接切成三刀：

| 段 | 规则 | 说明 |
|---|---|---|
| `events-adult-a` | `19 ≤ age[0] ≤ 30` | 求职 / 婚恋 / 首付，玩家停留最久 |
| `events-adult-b` | `31 ≤ age[0] ≤ 45` | 育儿 / 晋升 / 中年危机 |
| `events-adult-c` | `46 ≤ age[0] ≤ 60` | 子女成年 / 父母赡养 / 退休前 |

代价：文件从 4 个变 6 个（请求头 +0.8 KB）。收益：成年段内部也能按需，且**新增职业线事件可以按段归位**，S2 的内容增长不会单点膨胀。

> 这条我标为**建议**，不是必须。可以按阶段 B 落地时的事件实测分布再定。

**③ 加载时序（核心设计）**

```
首屏（defer）   data.js + events-child.js + 其余 6 个逻辑层文件
   │
   ├─ 童年段就绪后，立刻后台预取 events-student.js   ← 关键：余量近乎无限
   │
   ├─ 玩家进入 15 岁（离 19 岁还有 4 年）→ 预取 events-adult-a
   ├─ 玩家进入 27 岁 → 预取 events-adult-b
   └─ …
```

**策略一句话：永远比玩家多预取一段。** 玩家从当前段走到下一段至少要经历数年游戏时间（数年 = 数十次点击 = 现实里至少十几秒），预取余量是压倒性的。

**④ 兜底（必须写）**

```js
// drawEvent 之前：目标段未就绪时，从已加载段里抽
const pool = EVENTS.filter(ev => matchEvent(state, ev));
```

这一行**不用改**——因为未加载的事件根本不在 `EVENTS` 里，`filter` 自然只会从已加载的里面选。

**降级行为**：池子变小 → 事件重复率上升 → 但**绝不崩溃、绝不空池**（童年段 17 条足够撑过 0–6 岁，实测 0 岁只有 3 条可选）。这是**优雅降级**，不是故障。

**⑤ 读档处理（P2 唯一实质性的流程改动）**

```js
// importSave / 启动恢复
await ensureStagesLoadedFor(state.age);   // 按 age 同步补齐所有已开启段
renderGame();
```

`ui.js` 的启动/读档流程要从同步变异步。这是 P2 里唯一需要小心的地方，改动面约 10–15 行。

**⑥ 回归验证清单（阶段 B 的验收标准）**

| # | 断言 | 方法 |
|---|---|---|
| V1 | 拆分后 4（或 6）段按序拼接，**深等于拆分前 EVENTS** | 新建脚本，逐字段比对 241 条 |
| V2 | 每段内所有事件的 `age[0]` 落在本段区间 | 脚本扫描 |
| V3 | 事件 id 无重复、总数 = 241 | 现有 `sim-test.js` 已有此断言 |
| V4 | 全量 `tools/` 回归（含 `_verify-v51~v55`、`dom-test`、`browser-parity-test`）与改造前**结果一致** | `_run-tools.sh` |
| V5 | `robust-fuzz` / `coupling-probe` / `step-bench` 无回归 | 已有脚本 |
| V6 | 模拟弱网（DevTools 3G 节流）手动走完 0→100 岁，无空池、无报错、无重复段加载 | 人工 |

## 7. S2 如何做到「加内容不加首屏时间」

推演：事件 241 → 500（×2.07），新增事件按现有年龄分布均匀铺开，事件池 gzip 从 31.1 → **64.5 KB**。

| 方案 | 事件池 gzip | 首屏需下载的事件 | 首屏 FCP (3G) | 可开始游戏 (3G) |
|---|---:|---:|---:|---:|
| P0 现状 | 64.5 KB | 38.0 KB | **2778** | **2778** |
| P1 只加 defer | 64.5 KB | **64.5 KB（全部）** | 522 | **1147** |
| **P2 按阶段拆** | 64.5 KB | **4.6 KB** | **522** | **857（不变）** |
| P3 JSON + fetch | 64.5 KB | 0.0 KB | 522 | 857 |

**读法**：

- **P0（现状）**：事件翻倍 → `data.js` 从 53.6 涨到约 87 KB → 首屏从 2596 涨到 **2778 ms**。事件越多首屏越慢，S2 做完会肉眼可见地变卡。
- **P1**：FCP 锁死在 522 ms（defer 的功劳），但「可开始游戏」从 964 涨到 **1147 ms**——因为事件全量仍在关键路径上。**P1 挡住了 FCP，但挡不住事件膨胀。**
- **P2**：首屏只下载「当前人生阶段」的事件。500 条时童年段约 35 条 = **4.6 KB**。「可开始游戏」**依然是 857 ms，与 241 条时一模一样**。

> **这就是「加内容不加首屏时间」的量化证明**：P2 下首屏事件量 = f(当前所处人生阶段)，与事件库总量**无关**。S2 把事件加到 500、800、1000 条，只要每个阶段内部的事件数还在合理量级，首屏时间就是一条水平线。

补充：如果 S2 之后事件继续膨胀到单阶段也过大（比如成年段超过 40 KB gzip），就按 §6.3② 的思路继续细分——**这个结构是可以层层下探的，不会撞墙**。

## 8. 附带发现与建议（不在本方案范围，但相关）

### 8.1 brotli 的现成收益

| 压缩 | 全站 8 脚本 | 相对 gzip |
|---|---:|---:|
| gzip | 160.0 KB | — |
| **brotli** | **132.2 KB** | **−17.4%** |

GitHub Pages **自动**对静态资源做 brotli（浏览器 `Accept-Encoding` 带 `br` 时）。这一项**零改动、零风险**，只要确认线上确实在发 `br` 即可。建议阶段 A 顺手用 `curl -H 'Accept-Encoding: br'` 验一下 `Content-Encoding` 响应头。

### 8.2 CSS 是剩下的唯一渲染阻塞资源

FCP 关键路径 = `HTML 6.6 + CSS 6.5 = 13.1 KB`。P1 之后 CSS 就是全部瓶颈了。如果想再压，方向是「内联首屏关键 CSS + `<link rel="preload">` 异步加载全量」——**收益很小（3G 下约 35 ms），且引入构建步骤，不建议做**。零构建约束比这 35 ms 值钱。

### 8.3 事件搬家前，先让事件库定型

P2 的阶段 B 应该在 **S2 事件内容基本写完之后、大规模测试之前**做。理由是搬家 + 全量回归要花一次完整成本，如果搬完还要反复加事件，不如等定型。这也是为什么推荐「先 P1 立刻落地、P2 等一等」。
